# Security

Version 0.23.2. These are the limits that are actually in the code. Stylesheet, layout, and script limits are in `anvil-engine`. Network, sandbox, and profile limits are in this repository. Each tab has its own worker process, but the window process still fetches and paints.

Report problems in private:

https://github.com/buntatoes/anvil-browser/security/advisories/new

Problems in the engine can go there too, or to:

https://github.com/buntatoes/anvil-engine/security/advisories/new

Do not put the details in a public issue.

## What is on

- Linux: `PR_SET_NO_NEW_PRIVS`, core dumps off, and an attempt to cap address space at 2 GiB. `--renderer` asks for 256 MiB and exits if that cap does not stick.
- Each tab gets its own `--renderer` process the first time it opens an http, https or local page, and keeps it for later pages in that tab. It starts with an empty environment and `/` as its folder on Linux, so it doesn't get `DISPLAY` or anything else from the window's environment, and it has 5 seconds to say hello in the right protocol version. The document is parsed and its scripts run in the renderer, and the window waits at most 5 seconds for each answer. Messages use the binary format in `anvil_sandbox::wire`, with a size cap on every field and a navigation id on every request and answer. The window process sends the session cookie jar on the GET or POST and stores `Set-Cookie`. The renderer does not receive the jar. The window paints the returned document only when the renderer says it finished. A renderer that times out, exits, sends a bad frame, or answers for another tab or navigation is killed, the tab shows an error page without that document, and the next page in that tab starts a new renderer. After three such crashes in a minute, that tab shows an error page instead of starting another one, until the oldest crash is a minute old. Between pages, each renderer gets a heartbeat every 5 seconds and again before its next page: it has to answer a ping, and on Linux it is killed if it has used more than 1 second of CPU since it last finished a page. Closing a tab ends its renderer. `anvil://` pages are built in the window process. The renderer turns its own networking off when it starts and never holds cookies. For each linked script and each script `fetch()` it asks the window, which applies the shield, mixed content, HTTPS-only with your exceptions, the cross-origin resource policy, and the same-origin rule for `fetch()`, and sends back only the status, the content type and the body. Only script `fetch()` sends and stores cookies, in the window's jar. A renderer may ask for at most 512 fetches for one page and gets 60 seconds for the whole page, fetches included, or it is killed. Images, video and map tiles are loaded by the window for the page it draws, not by the renderer. A local page's own scripts are still read from disk by the renderer, and it still has your file access.
- Windows: a job object on the window process with a memory cap. The worker job, when used, also limits process count and UI rights.
- A panic in `execute_isolated`, or in a background page load, is caught.
- HTTPS on Linux goes through OpenSSL, with certificate checks. Windows uses Schannel.
- On Linux, the TLS handshake asks OpenSSL to offer X25519MLKEM768 first, then X25519, P-256, and P-384, with key shares for the hybrid and X25519. If this OpenSSL doesn't accept that list (it needs 3.5), a classical list is used, and if that fails too, OpenSSL's own defaults. A server without the hybrid gets a classical group. On Windows, Schannel negotiates TLS and queries `SECPKG_ATTR_CIPHER_INFO` / `SECPKG_ATTR_CONNECTION_INFO` after the handshake. The group the handshake really used is read back from OpenSSL or Schannel and shown on `anvil://security` for the last 16 connections made by the window process. A connection is only called post-quantum when that group includes ML-KEM. Tab renderers make no connections of their own. In addition, `anvil-net::pqc_tls13` has a self-contained RFC 8446 TLS 1.3 record and handshake state machine (`Tls13Stream`, `Tls13ClientHandshaker`, `Tls13ServerHandshaker`, `Tls13Session`) built on `anvil-pqc` and `anvil-cipher`, for `X25519MLKEM768` (`0x11EC`) and `X25519` (`0x001D`) key shares, TLS 1.3 `HKDF-SHA256` traffic and application keys, and `AES-256-GCM` record sealing and opening. Page loads don't use it: every real connection goes through OpenSSL or Schannel. Its self-test (`verify_pqc_hybrid_self_test`) runs once, before the first HTTPS connection, and if it fails no HTTPS connection is made.
- Over `https`, both Linux (OpenSSL) and Windows (Schannel `SECBUFFER_APPLICATION_PROTOCOLS`) offer HTTP/2 (`h2`) and HTTP/1.1 (`http/1.1`) through ALPN, and use HTTP/2 when the server picks it. Each page load or subresource opens its own connection and sends one request on stream 1. `anvil-net` also has a multi-stream client (`H2ClientSession::exchange` / `exchange_multiplexed`, odd stream IDs `1, 3, 5, ...`) and an origin-keyed connection pool (`connection_pool_stats`), but page loads don't use them yet. Server push is turned off. Frames over 16 KiB, header blocks over 256 KiB, decoded header lists over 64 KiB, and bodies over the 8 MiB raw cap are refused. Cookie and Authorization fields are never stored in the HPACK tables. If the server asks for HTTP/1.1 or refuses the stream before starting it, the request is sent again over HTTP/1.1 on a new connection. Plain `http` stays on HTTP/1.1.
- HTTPS-only mode, when on, sends every `http` request as `https`: the page, its redirects, and its images, stylesheets, and scripts, in the window, including the fetches it makes for a tab renderer. If the `https` request can't connect or its certificate fails, the tab shows a warning page and nothing is sent over plain `http`. The only way to use plain `http` in this mode is to allow that site, from the warning page or from `anvil://settings/permissions`. An allowed site also covers the hosts under it.
- `anvil://settings/permissions` keeps JavaScript (follow the main switch, allow, or block), cookies (allow or block), and plain HTTP (for HTTPS-only) per site, at most 512 sites. A rule covers the hosts under it, and the longest match wins. Blocked cookie hosts never store or send cookies, and their stored cookies are removed. Changes from that page carry a key made fresh each time the browser starts. A web page can link to an `anvil://` address but can't read the key, so a change without it is ignored. The switches and buttons on `anvil://settings`, `anvil://history`, `anvil://downloads`, and `anvil://home` need the same key. A web page's links and form actions can't point at `anvil://` addresses at all, and an `anvil://` address without the key only shows the page.
- Cookies are partitioned by the site of the top-level page (the last two labels of its host, or the whole address for an IPv4 host). A cookie is only sent while the top-level page is on the same site it was set under. Cookies saved before partitioning go into their own site's partition.
- Linux profiles (`profile.anvil`, including bookmarks, history, cookies, HSTS, settings, site permissions, and origin-partitioned `localStorage`) are AES-256-GCM from `anvil-cipher`. The key is `profile.key` (mode 0600) in the same directory, written before the profile. Windows profiles use DPAPI. `sessionStorage` is not in the profile. Each origin can store 64 KiB of `localStorage` or `sessionStorage` key and value bytes. A write past that cap leaves the previous value in place.
- Encrypted video samples are AES-128-CTR from `anvil-cipher`. CTR has no tag.
- Parsers in this repository, in `anvil-engine`, and in the sibling libraries reject oversized input.
- `anvil-net` blocks a fixed list of tracker host names before it connects.
- SHA-256 (`sha256-` via `anvil-cipher`) and SHA3-256 (`sha3-256-` via `anvil-pqc`) are used for Subresource Integrity checks, and SHA-256 is used for download records.
- PNG chunk checksums are checked in `anvil-image`.
- Stylesheet `width`, `height`, `max-width`, and offsets resolve `px`, `%`, `em`, `rem`, `ch`, `vw`, `vh`, `vmin`, `vmax`, and `calc()` combinations of `px`, `%`, `em`, and `rem`. Custom properties (`--*` and `var()`) stop after 8 nested substitutions. Any other unit becomes `auto`. A percentage height is `auto` when the containing block height is not set. `flex-grow` only distributes positive free space.
- Script `fetch()` is same-origin only. The Rust interpreter performs it. A cross-origin URL returns status 403 and does not connect. The numeric compiler does not perform `fetch()`. The interpreter keeps at most 256 KiB of a response body. `anvil-net` still stops at its raw and decompressed caps.
- WebAssembly 1.0 (`\0asm` version `1`) modules are validated and executed inside `anvil-script::wasm` with a 16 MiB (`256`-page) linear memory cap, a `500,000`-instruction execution budget (`MAX_WASM_STEPS`), and a `64`-frame call depth cap (`MAX_WASM_CALL_DEPTH`). Out-of-bounds memory accesses, division by zero, and step/depth exhaustion trap cleanly without panicking.
- YouTube, Gmail, Facebook, Instagram, X, Outlook, TikTok, LinkedIn, Reddit, other social hosts, and bank and payment hosts load through the normal HTTP path. External scripts on those hosts are not fetched. A script runs only when the code outside its quotes is at most 256 KiB. A `script` type that is not JavaScript is not executed. No API key is stored.
- Google Maps, OpenStreetMap, and `anvil://maps` are not loaded as those sites. This process fetches nine tiles at once and paints one bitmap. Tiles already fetched stay in memory for later pan and zoom. They are not written to the profile. OpenStreetMap comes from `tile.openstreetmap.org`. ArcGIS imagery, streets, and topo come from `server.arcgisonline.com`. A `webmap=` item is read from `arcgis.com` and one feature layer is queried, at most 80 features. A `token` on the address is sent only to an ArcGIS host and is not saved. OpenStreetMap hosts use the longer User-Agent. No maps API key is stored.
- Numeric x86-64 machine code. A `while` or `for` whose body is only numbers is compiled and the numbers are written back into the page script. The same loop may assign `document.getElementById("...").textContent` to a number. That one write calls back into the page. Other property reads stay on the interpreter. A whole script with no DOM, `fetch()`, or storage can take the numeric path. On Linux the page is mapped writable, filled, then marked read and execute, and calls use the System V argument order. On Windows the page is allocated with `VirtualAlloc`, and calls use `rcx`, `rdx`, and `xmm2`, with 32 bytes of shadow space. The caller owns the VM context. The worker process has its own context. This is not a general compiler.

## What is not on

- A renderer process that owns layout and painting. Workers parse and run scripts. The window process still fetches pages and subresources, keeps cookies, and lays out and paints each document.
- The real YouTube player bundle, the Gmail inbox application, the Facebook feed, the current Reddit application, and bank web apps. Those are script bundles this interpreter does not run. The HTML document is still loaded. A YouTube watch page adds a player built from YouTube's published JPEG frames, or a storyboard sheet when the page includes one. That player is not the H.264 stream, and no codec library was added. After Gmail's HTML sign-in form is posted, Google's own page says JavaScript is required. Reddit stays on the address you opened, including `www.reddit.com`, and is not sent to `old.reddit.com`. Requests to a Reddit host use a longer User-Agent that names this browser. A network-policy 403 is Reddit's, and this browser does not bypass it. No password is stored for a bank or a social site.
- A full-page GPU rasterizer. `anvil-raster` and `anvil-video` route rounded-rect box fills and opaque borders, blurred box shadows, linear gradients, and `NV12` / scaled video frame blits through `anvil_gpu::Compositor` (reusing a persistent thread-local `Compositor` and `GpuDevice` via `with_thread_compositor` / `with_thread_gpu_device` or `RasterEngine`), which runs on the GPU (Direct3D 11 on Windows, OpenGL 3.3 core on Linux) when the startup self-test passes bit-for-bit against the CPU, and falls back to the CPU otherwise. Square fills, text, and ordinary images stay on the CPU path (with bounded LRU glyph and image caches). Windows can also upload the finished CPU framebuffer to Direct3D 11 and compile `compositor.hlsl` to sample that upload; Linux copies pixels with X11. There is no GPU video bitstream decoder: the VA-API and Direct3D names in `anvil-video` are labels, and video packets are decoded on the CPU before `Compositor` blits the frames.
